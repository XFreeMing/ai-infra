# 从后端开发进入 AI Infra：源码学习路线

建立日期：2026-10-13。学习者有后端开发经验，AI Infra 从基础开始。Mac 用于阅读与分析；用户反馈另一台机器的 R0 验证已开始，结果尚未回传到本学习记录。

## 学习方式

当前先读 [QKV 个人学习复盘与源码调试路线](03-qkv-personal-review.md)：从实际提问定位数组身份、矩阵形状和计算去向的缺口，用同一组数字走完 Q/K/V、softmax、Wo 和残差，再分次回到调试器验证。

需要运行程序时，使用 [Mac 小模型调试练习](../../experiments/tiny-inference/README.md)：TinyStories 15M 约 61 MB，使用 llama2.c 在 CPU 上真实运行与下断点。每次只做 10–20 分钟，先看到 token、分数和生成循环，再把观察对应到 ds4。源码也用 submodule 固定，模型留在 Git 外。

每次围绕一个能解释的现象：先用普通语言建立概念，再读一个入口和少量关键代码，最后通过一个小问题检查理解。源码结论要能定位；类比只是帮助理解，不是实现事实。遇到陌生名词先说明输入、输出和作用，再补数学或硬件细节。

首条主线是 ds4，阅读版本固定为 `fc80bd695da76ee14bcb86820bf900a5cdfda806`。源码文件很大，按函数读，不要求从头通读。其他框架在相关专题中用于对照，并在开始该课时另行记录实际阅读 SHA；工作区升级不自动改写旧研究的版本。

一课可以分两次完成，不以“看完文档”作为掌握标准。每周 5–8 小时中，先安排两次 30–45 分钟导读，其余时间用于复述、追一段调用链及分析 PGX 回传证据。运行等待期间继续学习下一层概念；不修改实验正在使用的源码快照。

## 顺序与验收目标

| 顺序 | 主题与要回答的问题 | 先具备什么 | 源码切口 | 能做到什么才算理解 |
| --- | --- | --- | --- | --- |
| 1 | 一次请求如何变成输出？token、prefill、逐步生成分别是什么？ | 字符串、数组、循环、函数调用 | ds4 CLI 的 prompt 构造与普通生成循环 | 画出输入到输出；说明首 token 从哪里来 |
| 2 | 模型到底是什么文件？权重、向量、矩阵、tensor、GGUF | 第 1 课；会看数组维度 | `model_open`、形状校验、tensor 目录，与 R0 实际文件头对照 | 区分输入 token ID、模型权重、运行中间数据；解释为何文件可解析不等于能推理 |
| 3 | 模型怎样利用上下文？attention 与 KV cache | 向量/矩阵乘法的输入输出；不要求先推导训练 | 一层 attention 的参考实现，再看 session 状态 | 解释缓存保存什么、为什么减少重算、为什么仍占内存并参与后续计算 |
| 4 | 为什么需要 GPU？算力、内存带宽、kernel、异步执行 | tensor、乘法、prefill/decode、KV | backend 边界与一个小 kernel；CPU/Metal/CUDA 路径 | 区分计算量与数据搬运；知道提交结束不等于 GPU 完成 |
| 5 | 模型如何装得下？量化与 MoE | 权重、数值表示、内存与带宽 | R0 的 IQ2_XXS/Q2_K 配方、专家选择与执行 | 分清存储精度、计算路径和质量；解释“只激活部分专家”不等于只需保存这些专家 |
| 6 | 怎样服务多个人？会话、prefix cache、batch、调度与流式返回 | 一条请求的执行与资源占用 | ds4 server；再对照 llama.cpp、vLLM、SGLang | 解释单请求延迟、总吞吐和公平性的不同；区别 KV 状态与答案缓存 |
| 7 | 怎样判断优化有效？首 token 等待、生成速度、内存、正确性 | 阶段划分、运行环境和基本缓存行为 | `ds4-bench`、HTTP 计时、R0/R1 记录 | 为指标说清起止点、分母、冷热状态；保留失败和输出质量 |
| 8 | 怎样读一个真实优化？投机解码与回复边界恢复 | 采样、session/KV、测试和测量 | `fc80bd6` 与父提交、host mocks 和 HTTP 回归 | 说明假设、触发条件、状态正确性、收益边界和反例 |

这些是学习顺序，不是八项同时启动的任务。采样温度、概率分布在第 1 课只点到“选择策略”，进入投机专题前再补；训练优化器、反向传播、分布式训练和复杂 CUDA 优化按研究需要增加。

## 后端经验怎样迁移

| 熟悉的经验 | 可以借用的部分 | 类比的边界 |
| --- | --- | --- |
| 请求处理链 | 输入、校验、执行、输出和错误传播仍然适用 | 模型输出通常有逐步依赖，不能将未知的后续输出随意并行计算 |
| 进程级服务对象与请求上下文 | 用来区分加载的 engine 与每个 session 的状态 | 模型权重是训练得到的数值参数，不是业务规则表或答案数据库 |
| 缓存与增量计算 | 复用已有中间结果以减少重算 | KV cache 不是 prompt→完整答案的普通 key-value 缓存，KV 的名字来自 attention 的 Key/Value |
| 调度、排队、连接流 | 分析服务延迟、取消、限流和并发 | 多开请求不自动增加 GPU 吞吐；一个网络 chunk 也不一定是一个 token |
| 性能剖析与回归测试 | 固定条件、找瓶颈、验证行为、保留原始数据 | 更快输出错误答案不能算同等质量的优化；相同 seed 也不保证跨引擎逐 token 一致 |
