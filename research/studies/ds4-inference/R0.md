# R0：同一 GGUF 的静态兼容性核查与 PGX 准入清单

核查日期：2026-10-13。ds4 固定 `fc80bd695da76ee14bcb86820bf900a5cdfda806`；llama.cpp 固定 `972b5fcc19670e597f8de9bf5cacfb85752a5fff`。

## 结论与证据边界

**可以把同一份 Flash 0731 Q2 GGUF 作为首选对照候选。实际文件头与两个固定版本的源码之间，尚未发现阻断普通文本推理的格式冲突。PGX 运行准入仍未通过，不能宣称已经兼容或可以开始速度排名。**

本次完成了源码阅读、Hugging Face 公开文件身份核查、8 MiB HTTP Range 读取、GGUF 元数据与完整张量目录解析。没有获取完整模型，没有构建上游，没有连接 PGX 或运行推理。目录检查是本次实际执行的静态检查，不是作者报告，也不是执行了 llama.cpp loader。

机器可读证据：[R0_MODEL.json](R0_MODEL.json)。六个已冻结的输入探针：[R0_INPUTS.json](R0_INPUTS.json)。其中 token ID 尚未产生，明确为 null；不把 prompt 字节一致称为 token 已对齐。

## 1. 候选文件固定到什么程度

- 发布仓库：`antirez/deepseek-v4-gguf`。
- HF revision：`f71f23d552d664e523b422157b2befbf74040380`。
- 文件：`DeepSeek-V4-Flash-IQ2XXS-w2Q2K-AProjQ8-SExpQ8-OutQ8-chat-v2-imatrix-0731.gguf`。
- 大小：86,720,111,488 bytes，约 **80.7644 GiB**。
- HF LFS 报告的 SHA256：`ca22ae2f838e14077c22bc1c1417b71b45b5e5a3687bd96c2ac6e17fdb6261c0`。本机未读取全文件，不能称为本机已校验。
- [固定 revision 文件页面](https://huggingface.co/antirez/deepseek-v4-gguf/blob/f71f23d552d664e523b422157b2befbf74040380/DeepSeek-V4-Flash-IQ2XXS-w2Q2K-AProjQ8-SExpQ8-OutQ8-chat-v2-imatrix-0731.gguf)。下载时使用 JSON 中的固定 resolve URL，不使用 `resolve/main`。

ds4 的 [download_model.sh:10–22](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/download_model.sh#L10-L22) 指向该仓库与文件；下载实现使用可变的 [resolve/main:562](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/download_model.sh#L562)。`ds4flash.gguf` 还会随下载目标更新，所以实验必须传完整固定路径。

HF 页面上的模型卡主要描述早期非 0731 文件，自动生成的 “Use this model” 安装示例也不是本次版本的兼容性验证。候选身份以文件 API、固定 revision 和实际 header 为准。`0731` 与 `imatrix` 的来源说明仍依赖发布命名/上游指南；header 不提供完整原始 checkpoint revision、转换工具版本和校准集 hash。我们已锁定最终 artifact，尚未闭合整个权重生产链。

本次服务返回 `206 bytes 0-8388607/86720111488`。GGUF v3 的 metadata 结束于 5,248,096 bytes，tensor directory 结束于 5,333,793 bytes，按 32-byte 对齐后的数据起点为 5,333,824。前缀还包含少量 tensor 数据，但没有读取或校验完整权重。JSON 保存了 Range 和 header 的独立摘要，避免与全文件 SHA256 混淆。

## 2. 模型与张量匹配

| 实际 header 字段 | 值 | 核对意义 |
| --- | --- | --- |
| `general.architecture` | `deepseek4` | 与 llama.cpp V4 loader、ds4 V4 分支一致 |
| block / embedding / vocab | 43 / 4096 / 129280 | 符合 ds4 Flash 固定形状 |
| attention heads / KV heads / head dim | 64 / 1 / 512 | 匹配 attention tensor 形状 |
| experts / used / shared / expert width | 256 / 6 / 1 / 2048 | 匹配三组 routed experts 与 shared expert |
| SWA / indexer top-k / HC / Sinkhorn | 128 / 512 / 4 / 20 | 模型状态及计算语义 |
| compression ratios | 前两层 0；随后偶数层 4、奇数层 128 | 主干 43 层符合 ds4；数组还有第 44 个尾项 0 |
| gating / weight scale / normalization | sqrtsoftplus 枚举 4 / 1.5 / true | llama.cpp 强制要求相应 gating |
| train context / YaRN original / factor | 1,048,576 / 65,536 / 16 | 不是首次运行应分配的 context；首轮只设 4096 |

ds4 依据 [DS4_SHAPE_FLASH](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/ds4.c#L603-L638)、[config_validate_deepseek4_model](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/ds4.c#L6544-L6676) 校验。llama.cpp 的 [load_arch_hparams / load_arch_tensors](https://github.com/ggml-org/llama.cpp/blob/972b5fcc19670e597f8de9bf5cacfb85752a5fff/src/models/deepseek4.cpp#L19-L184) 读取相同语义；[tensor 命名映射](https://github.com/ggml-org/llama.cpp/blob/972b5fcc19670e597f8de9bf5cacfb85752a5fff/src/llama-arch.cpp#L559-L600) 对应实际 GGUF 名称。

本次将该 loader 的 Flash 主干规格独立转录后，与全部目录项比较：1,328 项名称和存储形状匹配，缺失/多余/维度不符均为 0。另检查 offset 对齐、量化 block 整除、区间不重叠及最后一个 tensor 的理论末尾恰等于文件大小。这个检查能排除明显的目录冲突，不能代替真实 loader 或权重完整性检查。

一个具体布局差异已经解释：`attn_output_a` 文件存 `[4096,8192]`，llama.cpp 视图为 `[4096,1024,8]`；loader 明确使用 `TENSOR_ALLOW_RESHAPE`，不是缺少维度或需要改写权重。

**MTP 元数据陷阱：**文件有 `deepseek4.nextn_predict_layers=1`，但没有 MTP tensors。llama.cpp 会探测 `blk.42.nextn.eh_proj.weight`，缺失即清零 nextn（上述 loader L20–25）。清零后保留 43 层主干。不能只看 metadata 就启动 MTP，也不能因此误判此文件必然加载失败。R0/R1 不加载 drafter，不开 MTP/DSpark；其 sidecar 是独立研究对象。

## 3. 量化是否真正一致

实际 tensor 目录计数如下，含 I32 路由表；不是按文件名推测。

| 类型 | tensor 数 | 主要位置 |
| --- | ---: | --- |
| IQ2_XXS | 86 | 43 层 routed gate/up |
| Q2_K | 43 | 43 层 routed down |
| Q8_0 | 345 | attention projections、shared experts、output 等 |
| F16 | 359 | embedding、router、部分 compressor/indexer/HC 等 |
| F32 | 492 | norms、sinks、bias、scale 等 |
| I32 | 3 | 前三层 hash-routing table |

类型编号与 [ggml.h](https://github.com/ggml-org/llama.cpp/blob/972b5fcc19670e597f8de9bf5cacfb85752a5fff/ggml/include/ggml.h#L388-L420) 一致。CUDA 的 [MMVQ 分支](https://github.com/ggml-org/llama.cpp/blob/972b5fcc19670e597f8de9bf5cacfb85752a5fff/ggml/src/ggml-cuda/mmvq.cu#L1344-L1380) 包含 Q2_K、IQ2_XXS；[MMQ 布局](https://github.com/ggml-org/llama.cpp/blob/972b5fcc19670e597f8de9bf5cacfb85752a5fff/ggml/src/ggml-cuda/mmq.cuh#L70-L95) 也处理这些格式。这只证明存在实现，实际模型图是否全部在目标 GPU 正确执行仍需检查。

首轮使用同一物理文件，禁止重新量化、换用类似名称 GGUF 或将 Q2 解释成 MXFP4。不同 KV/激活精度、ds4 `--quality`、kernel 默认近似仍可能造成输出差异，必须记录；同权重不是同数值路径。

## 4. tokenizer、模板与采样对齐

实际 header：`tokenizer.ggml.model=gpt2`、`pre=joyai-llm`；词表 129,280；`add_bos_token=false`、`add_eos_token=false`。模板本身会写 BOS，所以不能再额外添加一次。

关键 token：BOS=0、EOS=1、User=128803、Assistant=128804、`<think>`=128821、`</think>`=128822、DSML=128825。完整数组的编码摘要和模板 UTF-8 摘要已保存在 JSON；不把渲染结果中的全角竖线 `｜` 替换为 ASCII `|`。

单 user、无 system、无 tools、关闭 thinking 的目标输入为：

```text
<｜begin▁of▁sentence｜><｜User｜>{prompt}<｜Assistant｜></think>
```

这与 [ds4 encode_chat_prompt](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/ds4.c#L44300-L44328)、[score_llama 的 deepseek-ds4 renderer](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/gguf-tools/quality-testing/score_llama.cpp#L75-L79) 以及本次读取的 Jinja 模板静态逻辑一致。尚未执行 Jinja 或比较两侧真实 token。

必须显式处理四个差异：

1. **CLI 默认不同。**ds4 默认 system 是 `You are a helpful assistant`，默认 thinking 为 HIGH、context 32768、最多生成 50000。R0 显式设 `--system '' --nothink --ctx 4096 -n 32`，不能直接运行裸命令。[默认值](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/ds4_cli.c#L1921-L1940)
2. **分词实现独立。**ds4 手写 JoyAI 分割逻辑，llama.cpp 使用对应 regex；代码标点后换行、CRLF、中文数字和组合 Unicode 都要比 token ID。[ds4](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/ds4.c#L43949-L44010)、[llama.cpp](https://github.com/ggml-org/llama.cpp/blob/972b5fcc19670e597f8de9bf5cacfb85752a5fff/src/llama-vocab.cpp#L319-L328)
3. **评分工具不要用 auto。**`score_llama ... deepseek-ds4` 明确选择上述 renderer；auto 模板失败会落入 GLM fallback。prompt 以 `add_special=false, parse_special=true` 分词，continuation 则两者皆 false。[选择与分词](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/gguf-tools/quality-testing/score_llama.cpp#L238-L265)
4. **特殊标记的字面文本单独诊断。**普通 user 文本经过 BPE，与把整段渲染文本解析成 special tokens 可能不同。`literal_marker` 探针不进入首轮性能基线；出现差异先解释模板/转义契约，不立即归因于模型错误。

可复用的 token dump 入口：ds4 的 `--dump-tokens` 在正常 engine 启动之前调用只读分词路径；llama.cpp 有 `llama-tokenize --ids --no-bos --no-escape`，该工具在此版本默认解析 special tokens。保存 ds4 普通 chat、ds4 已渲染输入、llama 已渲染输入三份 ID 列表，区分 renderer 与 tokenizer 差异。[ds4 入口](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/ds4_cli.c#L2260-L2293)、[只读分词实现](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/ds4.c#L64770-L64819)、[llama 默认参数](https://github.com/ggml-org/llama.cpp/blob/972b5fcc19670e597f8de9bf5cacfb85752a5fff/common/arg.cpp#L1407-L1409)、[字节保留及分词](https://github.com/ggml-org/llama.cpp/blob/972b5fcc19670e597f8de9bf5cacfb85752a5fff/tools/tokenize/tokenize.cpp#L116-L185)。

R0 首次生成固定 temperature=0，关闭投机和跨请求 prefix 复用；保存 EOS/stop/截断原因。随机采样留到后续；相同 seed 不保证跨引擎随机输出相同。服务端 chat template、tool parser、reasoning 提取另做协议验证，不能用单 user 的对齐代替多轮/工具兼容性。

## 5. GB10 构建、内存与测量工具条件

| 条件 | ds4 | llama.cpp |
| --- | --- | --- |
| 构建路径 | `make cuda-spark`，实际映射 `compute_121a/sm_121a` | `GGML_CUDA=ON`；可显式设 `CMAKE_CUDA_ARCHITECTURES=121a-real` |
| 工具链 | ARM64 C/C++ host 工具、make、nvcc、cuBLAS；SBSA 库路径 | ARM64 C/C++、CMake、CUDA toolkit；核对生成的架构和实际 CUDA backend |
| CUDA 版本解释 | nvcc 必须识别目标架构，并编过该固定版本全部依赖 | 此版本 CMake 在 toolkit >=12.9 时加入 121a；不是“CUDA 12 任意版本即可” |
| 驻留 | Flash Q2 首选 resident，无 SSD、无单机 TP | 请求全部层 offload，实际日志确认；不能默认自动布局就是相同驻留 |
| 容量 | 80.7644 GiB 权重外还有重排副本、KV、workspace、系统占用 | 同文件不代表分配相同；保存实际内存、offload 与 swap |

依据：[ds4 架构/链接设置](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/Makefile#L39-L58)、[cuda-spark 目标](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/Makefile#L299-L312)、[llama CUDA 架构选择](https://github.com/ggml-org/llama.cpp/blob/972b5fcc19670e597f8de9bf5cacfb85752a5fff/ggml/src/ggml-cuda/CMakeLists.txt#L53-L112)。12.9 是已读构建分支的门槛，不能由此保证 ds4 全部代码或任何驱动组合可运行；以实际编译/链接/加载为准。

PGX 先记录 `uname -m`、`nvidia-smi`、`nvcc --version`、host compiler/CMake 版本、内存/swap、磁盘空闲与正在占用 GPU 的进程。`nvidia-smi` 所示 CUDA 上限不等于已安装 toolkit。工作负载一次一个，不同时启动两套大模型；不擅自停止其他任务。

已有 `score_llama` 可作为质量比较起点，但它的 [Makefile 默认路径](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/gguf-tools/Makefile#L1-L8) 指向作者另一个 checkout，必须覆盖 `LLAMA_CPP_DIR`、`LLAMA_CPP_BUILD`、`LLAMA_CPP_BIN`，并用 `ldd` 核查真实库。不要只固定子模块却链接系统旧版 libllama。先在独立快照构建 ds4 CUDA，再构建 scorer，防止 gguf-tools 自己的默认参数混入另一套构建。

## 6. PGX 上按顺序验收

| 顺序 | 验证项目 | 保存的证据 | 通过条件/失败处理 |
| --- | --- | --- | --- |
| P0 | 独立实验 clone 与主仓库/两个子模块版本 | 完整 SHA、clean 状态 | 不更新正在运行的 checkout |
| P1 | 硬件、toolkit、编译器、内存与磁盘 | 环境文本、占用、驱动信息 | 有容量再准备权重；有冲突先排期 |
| P2 | 同一个固定 GGUF | 完整路径、bytes、`sha256sum`、header dump | SHA256 与 R0_MODEL 的 HF LFS 值一致，否则停止 |
| P3 | 两套 CUDA 构建 | 编译日志、架构、二进制路径/hash、动态库路径 | 均从指定源码构建；构建失败也是 R0 结果 |
| P4 | 六个输入探针的 byte/token 对齐 | JSON 输入 hash、rendered bytes、三组 token IDs | baseline 三项一致；边界项差异解释后限定适用域 |
| P5 | 分别加载同一文件 | metadata、43 主干层、实际 offload、内存、KV 配置 | 无未知 tensor/kernel/缺权重错误；无未解释 CPU fallback |
| P6 | 一个短 prompt、32-token 生成 | 完整参数、原始输出、退出码、EOS/stop、资源轨迹 | 非空、无损坏/NaN/崩溃；两边严格串行 |
| P7 | 固定 continuation 保真初筛 | 相同 token 历史、NLL/top-token、grader 与库来源 | 明显差异先定位模板、量化/数值路径，不直接跑长 benchmark |

P4 使用 tokenizer 工具，不做推理；但工具可能要求完整合法 GGUF，不把本次截断的 8 MiB 前缀伪装成模型。文本写入时保留原始 UTF-8、CRLF、尾空白，不经 shell `echo` 隐式加换行。普通探针显式关闭 system/thinking；已渲染输入不再套第二层模板。

首次 PGX 会话分为准备与验证两段：下载/构建单独计时。加载加短生成初始预算每个引擎 10 分钟，超时保存日志并停止该组，不自动追加更长任务；这是停止规则，不是速度预测。持续 swap、OOM、输出损坏、kernel 错误或资源干扰都暂停。P7 先 3 条短 continuation，不运行完整质量集。通过后再安排 R1 的 1K/8K/32K 矩阵。

如果相同 GGUF 在一侧失败，记录具体 metadata/tensor/op/backend 错误；不偷偷重转 GGUF 后继续称“同权重”。若仅模板不一致，先隔离到相同 token 历史；若只能换权重或使用 SSD/CPU offload，转为部署方案比较。PGX 验证通过前，R0 整体状态保持 pending。

## 本次交接

- 下一步：在 PGX 执行 P0–P3，条件齐备后只做 P4–P7 的有限验证，再更新本页状态。不会把目录匹配结果写成 GPU 兼容认证。

English recap: The pinned GGUF is a viable same-file candidate at the metadata and tensor-directory level. Runtime loading, token alignment, memory residency, and numerical fidelity remain PGX admission checks.
