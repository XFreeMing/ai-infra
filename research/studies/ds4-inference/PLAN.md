# ds4 调研与实验计划

日期：2026-10-13。适用条件：Mac 做 AI 辅助阅读与分析，单台 PGX GB10 做验证，每周主动投入 5–8 小时。

本文件是后续工作计划；尚未下载权重、构建上游、运行 GPU 测试或形成速度排名。首轮静态发现见 [总览](README.md)、[源码地图](SOURCE_MAP.md)、[证据审计](EVIDENCE.md)、[对比矩阵](COMPARISON.md)。

## 目标与范围

第一份成果回答一个窄问题：**相同 Flash 0731 权重在单 GB10 上，ds4 的实际交互代价是什么；一个明确的状态恢复优化是否减少多轮等待，同时保持正确性？**

第一直接比较对象是 llama.cpp。vLLM/SGLang 先形成有源码依据的架构与可部署性清单，通过权重、kernel、内存和语义门槛后再加入运行矩阵。先读 V4 Flash，V4.1、GLM、Qwen 的发现作为边界材料；不同时展开所有模型。

比较分三层，结果分别写表：

1. 同 checkpoint、同一 GGUF、同输入 token 的引擎实现差异。
2. 同硬件可用配置的速度—质量—容量取舍，允许权重/精度不同，但不能把差异只归因于引擎。
3. 调度、缓存、投机和 SSD 策略的源码学习；尚不能运行时只给机制比较。

## R1：最小同权重基线

阶段 A：两个引擎各做 1K 输入、32 输出的试跑。通过后做 1K/8K/32K 输入、256 输出、并发 1，每格三次，共 18 个性能运行单元。32K 只有在内存与正确性检查通过后才加入。

固定条件：同一 GB10、同一 GGUF、同一请求集合；关闭投机，显式对齐 thinking、采样、停止策略及可对齐的 KV 配置。首次 prompt 使用新会话或清空该引擎自身前缀状态；不把需要全机清理页缓存的“冷磁盘”混进每次普通基线。

输入提前冻结为 JSONL 与实际 token 清单，保留 hash。不要让两个引擎各自生成随机 nonce/随机语料。固定输出 token 数的探针只用于性能；自然 EOS/stop 的任务效果另算。

执行顺序交错，例如 A/B/B/A，再补齐同等次数，减少温度、系统缓存和后台状态漂移。至少一次预热，预热与加载时间单独记录。计时需等待实际 GPU 工作完成，不能只测异步提交。

| 指标 | 明确定义 |
| --- | --- |
| 加载/准备时间 | 模型打开、repack/编译缓存构建、ready 之前的耗时；与热启动分列 |
| fresh prefill | 从空会话处理完整输入；与 continued prefill 的新增部分分列 |
| 引擎 decode | 标明 greedy 或 teacher-forced、是否含第一 token、tokens 分母和同步方式 |
| HTTP TTFT | 客户端发送请求到收到第一个有效输出；说明是否包括 reasoning，不能用 `gen_first_ms` 代替 |
| TPOT / chunk 间隔 | 平均 TPOT 与 SSE chunk 间隔分开命名；一个 chunk 可能含多个 token，不能冒充逐 token ITL |
| 端到端 | 从请求开始到正常完成，含排队与协议开销，保存完成/错误原因 |
| 内存与 SSD | 实际统一内存占用、进程 RSS/PSS 等可用指标、swap、读盘量；避免把共享内存重复相加 |

每格报告三次原始值、中位数与范围，保留时间序列。三次请求不足以给可信的请求级 p95；若进入 R6，先确定样本数量与重复批次，再报告尾延迟及不确定性。

资源预算：模型下载、构建单独计时；正式 R1 首轮墙钟上限建议 90 分钟，不作为耗时预测。先测短样本再按结果设每格 timeout；总预算将耗尽时缩减矩阵并报告缺项。内存不足、持续 swap、输出异常或其他进程干扰时停止该组。

## R2：把 fc80bd6 变成第一项真实机制验证

对照版本为 `d6b516abb4a286a423fdb4071a19f86a3d9ab9c0` 与 `fc80bd695da76ee14bcb86820bf900a5cdfda806`；后者的父提交就是前者，减少无关变更。

研究链：[server 边界回退](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/ds4_server.c#L12583-L12608) → [有界状态恢复](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/ds4.c#L86725-L86821) → [回归测试](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/tests/test_dspark_rewind.py)。

先读 `test_dspark_rewind.py`：它抽取生产 helper，但用有界 host mocks 验证状态转移；可在 Mac 学习控制流，不能证明真实 GPU/KV/logits 正确。`test_server_speculative_stop.py` 则请求已运行的服务，保存双轮 HTTP 原始记录；其 `approx-tokens` 是字符估算，TTFT 计非空内容/reasoning/tool delta，且不提供内部状态 oracle。

以 HTTP 用例为起点，在真实服务日志中确认触发条件，再冻结两个版本共用的外部 harness 和请求；不能假设旧提交已有新测试文件，也不能将只在 mock 中触发的故障称为 GPU 复现。内部状态检查需另用受控的 teacher-forced 对照或 backend instrumentation。使用同一 Flash 0731 target/support 文件、同一编译参数、同一服务协议与采样模式；single-Spark 验证不扩展到双机 TP。

比较四类情况：正常无回退；在 accepted block 内结束；工具语法导致采样模式切换；快照过旧/失效需 fallback。先确认日志真的命中新路径，再考虑长上下文。

上游双轮脚本会把各自实际第一轮回答带入第二轮；若两个版本的回答不同，第二轮负载也会不同。用于纯机制计时的对照必须固定相同 token 历史与边界条件，必要时另做受控状态探针；沿用自然回答的运行单列为端到端任务对照，保留实际 token 数，不能将全部耗时差归因于 rewind。

观察 `rewind_ms`、replay token 数、重复 prefill token 数、第二轮 TTFT、整轮完成时间、输出与 logit/状态检查。新 trace 字段在旧版本可能不存在，跨版本计时以统一客户端/harness 为主，trace 用于解释机制。

验收：能解释触发条件；正确性检查通过；报告每种 case 的时间变化和至少一个无收益/回退边界。若没有命中快照恢复，则结论是“此负载未触发优化”，不能据此判定优化无效，也不能宣称有提升。

## R3–R7 的设计约束

- **R3 投机：**先做 T=0 的普通/DSpark；随后 T>0 的普通、exact、opportunistic 三组。固定完整采样参数，并记录两种投机模式的 confidence 阈值、draft 深度和自适应调度。代码与散文分组；看接受率、重复/退化、代码测试成功率及 time-to-valid-answer。统计上同分布不要求同 seed 产生完全相同文本。
- **R4 缓存：**先固定同一量化，不允许跨量化缓存复用污染基线；使用不同缓存目录或支持的 reject-different-quant 设置。分别看 live、disk restore、全量重建及短工具结果追加。缓存命中、恢复花费与重建花费分别记录。
- **R5 效果：**先同权重 default/quality，再做权重量化轴。固定修正后的 grader 与匹配 checkpoint 的 continuation fixtures；0731 的旧 API 已变化时，不能用新的线上响应充当相同 checkpoint 的参考。保留 token 对齐失败与被排除位置数。
- **R5 任务集：**先冻结小型独立回归集，如 8 道带测试的代码题、6 个工具/JSON协议案例、6 个可验证长上下文检索案例。记录题目来源、expected、判分器、生成预算、失败/截断；随机模式预先固定多次采样规则。该集用于发现回退，不称标准排行榜。
- **R5 量化：**Q4/mixed 如果不满足本机内存条件，明确转入容量方案或保留为文献证据；不通过更换机器获得数字后仍标为单机同条件。报告 NLL/概率保真及任务结果；预先约定等价容忍范围，置信区间包含零不等于证明等价。
- **R6 并发：**先 C=1/2，能解释内存和调度路径后才开 4。固定闭环并发或开环到达过程，二者不混用。每客户端速度与 aggregate 吞吐分开。vLLM/SGLang 仅在 R0 门槛通过后参加，不把双 Spark 的总量放进单 Spark 表。
- **R7 SSD：**固定模型、实际 expert cache 容量、预加载及冷/热条件；流式缓存与操作系统 page cache 分别记录。先测很短生成，再决定长任务。CUDA 整层预取的已读生产路径是 V4.1 prefill、`total_count >= 2048` 且 cache 足够两层全部 experts；不把相关开关当 V4 Flash 普通 decode 的通用消融。

每周约 2 小时资料/作者讨论、2 小时源码阅读、1–2 小时设计与启动、0–2 小时分析整理。GPU 等待不占主动学习预算；一次只安排一个主要性能实验。下载或兼容性问题超出预算时顺延，并记录原因，不用增加项目功能掩盖缺少研究结果。

沿用[双机工作流](../../../docs/workflow.md)：每次运行有独立 clone 与环境，固定主仓库及子模块提交。对照两个 ds4 版本时，各自形成明确的主仓库实验快照；不要切换正在运行的源码。结果通过独立整理目录回流 Mac。

## 每个实验的交付标准

1. 明确假设、对照变量、能推翻假设的结果和已知混杂因素。
2. 代码/权重/输入/grader 的固定身份，实际构建与执行路径。
3. 完整命令、环境、预算、运行编号、退出原因与失败数据。
4. 原始逐次测量与可重建图表；大产物的位置、校验值及取回方式。
5. 正确性/任务效果、时间与资源三方面同时解释，指出不支持结论的结果。
6. 发布时明确“上游报告、静态推断、本机实测”的证据类别。
